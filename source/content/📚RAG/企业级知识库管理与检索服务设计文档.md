# ikb-retriever-service

项目地址：[https://gitlab.juewei.cn/juemind/ikb-retriever-service.git](https://gitlab.juewei.cn/juemind/ikb-retriever-service.git)

知识库管理和检索的基础服务，提供文档解析、向量化存储、结构化检索能力，支持作为 RAG 系统的数据层和检索层。

## 📋 项目定位

核心定位：知识库管理 + 检索服务

本项目是一个知识库管理和检索的基础设施服务，提供：

● 知识管理层：知识库的 CRUD、文件管理、权限控制

● 文档解析层：多格式文档解析（PDF、DOCX、TXT、MD 等）

● 向量化存储层：文档内容的向量化、存储到 Milvus

● 检索服务层：结构化检索、全文检索、向量相似度检索

重要说明：

● ❌ 不是一个完整的 RAG 问答系统

● ❌ 不包含 AI 回答生成能力

● ✅ 是 RAG 系统的数据层和检索层，可作为上层 AI 应用的基础服务

● ✅ 是可扩展的检索能力底座，支持作为 MCP (Model Context Protocol) 工具服务

与产品设计的区别：

● 本项目专注于知识管理 + 检索增强，不包含回答生成

● 可以作为上层 AI 应用（如 Agent、Chatbot）的数据源和检索工具

### 技术选型说明

#### 为什么选择 Sanic？

选型理由：

● 异步高性能：基于 asyncio，性能接近 Go 和 Node.js

● 简单易用：类 Flask 语法，学习成本低

● 生态完善：支持 WebSocket、GraphQL、请求上下文等

● 生产就绪：被多家大型企业用于生产环境

对比其他框架：

● Flask：同步框架，性能不如 Sanic

● FastAPI：功能更强大，但过度设计，我们只需要简单的 Web 框架

● Tornado：学习曲线陡峭，生态不如 Sanic

#### 为什么选择 Milvus 作为向量数据库？

选型理由：

● 高性能：支持十亿级向量检索，毫秒级响应

● 云原生：支持容器化部署，云原生架构

● 可扩展：支持分布式部署，横向扩展

● 多种索引：支持 IVF_FLAT、IVF_PQ、HNSW 等多种索引类型

● 阿里云托管：使用阿里云 Milvus 实例，免去运维成本

对比其他向量数据库：

● Pinecone：商业产品，成本高，数据在国内

● Weaviate：功能丰富但性能不如 Milvus

● PGVector：PostgreSQL 插件，性能有限，不适合大规模数据

#### 为什么选择 IVF_FLAT 索引？

选型理由：

● 精确度高：IVF_FLAT 是精确索引，召回率 100%

● 性能平衡：在速度和精确度之间取得平衡

● 适合中等规模：当前数据规模在百万级，IVF_FLAT 足够

● 构建快速：索引构建时间短，适合频繁更新

其他索引类型对比：

|   |   |   |   |
|---|---|---|---|
|索引类型|特点|适用场景|优缺点|
|IVF_FLAT|倒排文件 + 精确搜索|中小规模、高召回要求|✅ 精确度高，❌ 查询速度较慢|
|IVF_PQ|乘积量化压缩|大规模、内存受限|✅ 内存占用小，❌ 精确度降低|
|HNSW|图层级索引|超大规模、高性能|✅ 查询速度快，❌ 构建慢、内存占用大|
|FLAT|暴力搜索|小规模、精确搜索|✅ 100% 召回，❌ 大数据集性能差|

未来优化方向：

● 数据量超过千万时，考虑切换到 HNSW

● 内存受限时，考虑 IVF_PQ

#### 为什么选择 COSINE 距离度量？

选型理由：

● 语义相似：余弦相似度关注向量方向，不受向量长度影响

● 文本检索最佳：对于文本 Embedding，余弦相似度效果最好

● 范围归一化：结果在 [0, 1] 之间，便于设置阈值

距离度量对比：

|   |   |   |   |
|---|---|---|---|
|度量类型|计算方式|适用场景|说明|
|COSINE|1 - cosine_similarity|文本、语义检索|✅ 关注方向，❌ 忽略长度|
|L2（欧氏距离）|sqrt(sum((a-b)^2))|图像、位置数据|✅ 综合考虑方向和长度|
|IP（内积）|dot(a, b)|归一化向量|等价于余弦（向量归一化时）|

#### 为什么选择通义千问 text-embedding-v3？

选型理由：

● 中文优化：专门针对中文场景优化

● 性能优异：在中文文本检索任务上表现优秀

● 成本优势：国内服务，价格更低，延迟更小

● 稳定可靠：阿里云提供，SLA 保障

Embedding 维度：1024 维，平衡了表达能力和计算效率

选型理由：

● 配置热更新：无需重启服务即可更新配置

● 多环境管理：支持 dev、prod 等多环境配置

● 版本管理：配置历史版本回滚

#### 为什么选择 Redis 作为任务队列？

选型理由：

● 简单可靠：List 结构实现队列，LPUSH + BRPOP

● 持久化：支持 RDB 和 AOF 持久化

● 分布式锁：Redlock 算法实现分布式锁

● 高性能：内存操作，毫秒级响应

● 集群支持：支持 Redis Cluster 集群部署

对比其他消息队列：

● RabbitMQ：功能强大但复杂，运维成本高

● Kafka：适合高吞吐场景，过度设计

● Celery：功能丰富但依赖多，我们的场景简单

#### 为什么选择 Tortoise-ORM？

选型理由：

● 异步原生：基于 asyncio，与 Sanic 完美配合

● 类 Django ORM：语法类似 Django，学习成本低

● 类型提示：支持 Pydantic，类型安全

● 性能优秀：异步数据库操作，并发性能好

对比其他 ORM：

● SQLAlchemy：功能强大但复杂，异步支持不够成熟

● Django ORM：同步框架，无法在 Sanic 中使用

#### 为什么选择 Redis 作为缓存？

选型理由：

● 高性能：内存操作，读写速度快

● 数据结构丰富：支持 String、Hash、List、Set、ZSet

● 持久化：支持 RDB 和 AOF 持久化

● 集群支持：支持 Redis Cluster 集群

● 简单易用：API 简单直观

缓存策略：

● 热点数据缓存（如知识库列表）

● 查询结果缓存（如检索结果）

● 会话缓存（如用户会话）

#### 为什么自己实现操作符拼接？

问题背景：

●  项目需要支持复杂的过滤条件，包括：普通字段的操作符：file_id__in=[1,2]、chunk_id__gte=100

● JSONB 嵌套字段的操作符：metadata__product_name__icontains="鸭脖"

● AND/OR 逻辑组合：{"isOr": true, "filter": {...}}

为什么不能直接用 ORM？

Tortoise-ORM 的限制：

```
# ❌ ORM 不支持 JSONB 嵌套字段查询await KbItem.filter(metadata__product_name__icontains="鸭脖")# 报错：Unknown field metadata__product_name for model KbItem
```

我们的解决方案：

自己实现了一套操作符解析和 SQL 拼接系统（app/manager/items_manager.py）：

```
# ✅ 支持的操作符格式{    "file_id__in": [1, 2],              # IN 操作    "chunk_id__gte": 100,                # 大于等于    "metadata__product_name__icontains": "鸭脖",  # JSONB 嵌套字段 + 模糊查询    "metadata__price__lte": 50           # JSONB 嵌套字段 + 小于等于}
```

实现原理：

1.  解析操作符：按 __ 分割字段名和操作符

a.  field__icontains → field + icontains

b.  metadata__product_name__icontains → metadata + product_name + icontains

2.  分类处理：

a.  普通字段：使用 ORM 的 Q 对象查询

b.  JSONB 字段：拼接原生 SQL，使用 PostgreSQL 的 #>> 操作符

3.  SQL 拼接示例：

```
# 查询条件{"metadata__product_name__icontains": "鸭脖"} # 生成的 SQLWHERE metadata #>> '{product_name}' LIKE '%鸭脖%'
```

支持的操作符（详见附录 A）：

● 比较类：eq、ne、gt、gte、lt、lte

● 集合类：in、notin

● 字符串类：contains、icontains

● 空值类：isnull、notnull

为什么这样做？

|   |   |   |
|---|---|---|
|方案|优点|缺点|
|ORM 查询|类型安全、易读|❌ 不支持 JSONB 嵌套查询|
|原生 SQL|功能完整、性能最优|✅ 自己实现操作符解析<br><br>✅ 需要手动防止 SQL 注入|
|混合方案（我们选择）|结合两者优势|简单场景用 ORM，复杂场景用原生 SQL|

代码位置：

● app/manager/items_manager.py:_split_filters() - 解析操作符

● app/manager/items_manager.py:_build_where_clause() - 拼接 SQL WHERE 子句

● app/manager/items_manager.py:_build_base_filters() - ORM 查询（不支持嵌套字段）

## 🔬 Agentic RAG 预研（实验性功能）

⚠️ 注意：以下内容为预研性质的实验性功能，仅供参考，不建议在生产环境使用。

### 当前实现概览

项目在 app/controller/agent/ 目录下包含基于 pydantic-ai 的 Agent 检索框架：

1. 检索 Agent（Retrieval Agent）

● 分析用户查询意图

● 识别内容类型（QA/DOCUMENT/PRODUCT 等）

● 生成结构化查询参数（StructQueryParams）

2. 评估 Agent（Evaluation Agent）

● 评估检索结果相关性

● 决策：stop（满意）/ continue（继续检索）/ revise（修正查询）

3. 知识库搜索工具（KbSearchTool）

● 位于 app/manager/agent/kb_search.py

● 执行结构化查询和向量检索

A: 在 app/config/content_schema.py 中添加新的 ContentSchemaType 和字段定义。
