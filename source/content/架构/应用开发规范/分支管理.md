### 普通业务项目分支管理规范

|   |   |
|---|---|
|分支名|说明|
|master|主分支，保持干净，仅用于正式版本发布。版本迭代或bug修复需从该分支拉出新分支进行开发。|
|v4.x.x-2025xxxx|开发分支，用于版本功能开发，命名格式为版本号+日期，如 v4.1.0-20250601。|
|fix4.x.x-2025xxxx|修复分支，用于bug修复，命名格式为 fix+版本号+日期，如 fix4.1.0-20250603。|
|test|测试环境发布分支，所有开发完成并联调提测的代码合并至该分支，部署到测试环境。|
|release|正式发布分支，验收通过的分支合并至此分支，并打上Tag进行发布。发布完成并回归测试无误后，将该分支内容合并至 master。|

### **分支管理的优势：**

master 分支始终保持干净，仅接受来自 release 的合并，避免因开发失误造成污染。

开发分支/修复分支只来自master分支 始终保持一个版本一个分支的拉取

release 分支仅合并已通过测试的开发或修复分支，并统一打上Tag，有助于版本管理与问题回溯，支持快速回滚至历史稳定版本。

如果有两个或者多个开发分支并行怎么办？

从master拉取2个独立的分支进行开发 可以按照版本号的顺序依次合并test分支进行（提测或者联调） 然后依次进行合并test rebase 并合并到 release 当两个分支版本 A分支上线了之后 B分支还在开发或者测试阶段 这个时候release分支将最新代码手动合并至master之后 此时B分支的开发分支已不是最新代码了 需要手动将B分支rebase到master， 按照顺序一次提测上线 形成闭环

### 开发环境管理建议

目前项目缺乏独立的 dev 开发环境，也缺乏预发布环境，开发与测试均在同一测试环境进行联调与验证，容易导致测试数据污染等问题。

**建议如下：**

- 明确区分 开发环境（dev） 与 测试环境（test），保障测试环境的稳定性与纯净性；
    
- 明确区分 测试环境（test）与预发布环境。
    
- 所有日常开发、联调应优先在独立的 dev 环境完成；
    
- 提测前将代码合并至 test，并部署至测试环境，供QA进行功能与回归测试；
    
- 测试通过后进入预发布流程。
