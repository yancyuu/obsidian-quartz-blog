## 后端项目代码规范

技术栈：sanic，asyncio，langgraph，langchain

### 🧱 一、目录结构规范

|   |   |   |
|---|---|---|
|层级|职责关键词|示例|
|services|路由，数据协议可插拔（千万别再这里堆业务）|kb_service|
|controller|校验，业务逻辑|create_kb(data: KBRequest)|
|models|ORM 数据模型|class KnowledgeBase(Model)|
|scheme|数据结构、错误码|class KBRequest(BaseModel)|
|common_sdk|日志、权限、工具|logger, message_id 等|
|ai_sdk|构建者模式，封装ai通用函数|自己研究|

```Python
app/                    # 主业务应用目录
├── agent/              # 智能体模块（如有多个 Agent 组件）
├── config/             # 配置项加载与解析（如环境变量、全局参数）
├── controller/         # 业务逻辑服务层：处理核心业务（不直接依赖 web 框架）
├── models/             # ORM 模型层（如使用 Tortoise/SQLAlchemy）
├── scheme/             # 数据结构：Pydantic 请求体、响应体、错误码定义等
├── services/           # 路由层：处理请求、输入校验、调用 controller
│   ├── 
__init__
.py
│   └── api_service.py
common_sdk/             # 通用工具：日志、异常、鉴权、数据库连接池等可复用模块
ai_sdk/                 # ai-SDK：如大模型、向量搜索、AI能力封装
script/                 # 脚本工具：如导入、迁移、数据修复等
```

> ✅ 保持单一职责，服务层只做请求接入，控制器只做业务逻辑，模型只定义数据结构。

### 🔧 二、文件命名规范

- 一律使用 **小写 + 下划线风格（snake_case）**。
    
- 文件名应表达明确含义，如：
    
    - `user_controller.py`：用户相关控制器
        
    - `kb_service.py`：知识库相关业务逻辑
        
    - `db_utils.py`：数据库相关工具函数

### 🧬 三、模块职责划分规范

1. #### `services` 路由层
    
    - **路由与协议适配** 当前 `service` 层仅负责 **接收 RPC 风格的 HTTP+JSON 请求**，并将参数解析后调用下游业务逻辑（Controller）。
        
    - **接口可扩展** 虽然暂时只实现 JSON，但设计时要保持“接口不动、协议可替换”原则，以便将来改为 Protobuf-over-HTTP 或者直接全面切换到 gRPC。
        
    - **新增协议**
        
        - 若需要添加 WebSocket、RESTful/API Gateway、或 Protobuf-over-HTTP，只需在 `service/` 下创建新的子目录（如 `service/ws/`、`service/proto/`），复用现有 Controller，无需修改业务逻辑。
            
    - **“接口不动、协议可插拔”**
        
        - 保证路由层把请求体解析→调用 Controller→返回结果这三步与数据格式（JSON、Protobuf）区分开来。
            
        - Controller 只关心“业务输入”→“业务输出”，不依赖任何传输细节。
            
    

- 仅负责处理 HTTP 请求、调用 `controller` 层、构造响应。
    
- **严禁在** **`services`****中直接写业务逻辑或 SQL。**
    
      
    

2. #### `controller/` 控制器层
    
    - **职责分离**
        
        - Controller 层只关心“接受纯 Python 参数 → 执行业务 → 返回纯 Python 结构”。
            
        - 路由层（Service）负责“请求体解析（JSON → dict）→ 驼峰/下划线转换 → 调用 Controller → Controller 返回 Python dict → 包装成 JSON → 发送响应”。
            
    - **跨协议复用**：未来可以把 Protocol Buffer 或 gRPC 路由也调用同一套 Controller。
        
    - **降低冗余**：**业务代码不会散落在 Blueprint 装饰器内部；可以用单元测试直接调用 Controller。**
        
    - **部署灵活：未来要拆分 gRPC，只需在** **`service/grpc/`** **新加逻辑，Controller 保持不变。**
        
    
      
    

3. #### `models/` ORM模型层
    
    - 使用 `Tortoise ORM` 或 `SQLAlchemy` 定义数据库结构。
        
    - 保持和数据库表结构一致，字段注解清晰，使用 `description` 做好文档说明。
        
    - 添加通用方法如 `.to_dict()`，便于返回 JSON。
        
    

4. #### `scheme/` 数据结构与校验
    
    - 使用 `Pydantic` 定义请求体、响应体、错误码等。
        
    - 所有接口入参统一校验，放在 controller 入口。
        
    - 所有响应体建议统一格式，例如：
        
    

```Markdown
{
  "code": 0,
  "msg": "success",
  "data": {}
}
```

## ⚙️ 四、开发规范

**按模块做命名空间（RPC 风格命名规范）HTTP/Sanic + RPC + JSON**

1. ### 前缀分组
    
    - **统一路径前缀**：在 `service/http/` 目录下，为每个模块（如 KB、Policy、User）用 Sanic Blueprint 定义 RPC 风格的路由：
        
    
    ```Bash
    POST /kb/get       → Body(JSON) { "id": "..." }  
    POST /kb/list      → Body(JSON) 可选 { "page":…, "pageSize":…, "filters":…, "orderBy":… }  
    POST /kb/create    → Body(JSON) { …创建字段… }  
    POST /kb/update    → Body(JSON) { "id": "...", …更新字段… }  
    POST /kb/delete    → Body(JSON) { "id": "..." }  
    ```
    
    - **新增操作**：如果后续要加 `bulkImport` 或 `rebuildIndex`，只需在同一目录下新增：
        
        ```Markdown
        POST /kb/bulkImport  
        POST /kb/rebuildIndex  
        ```
        
    

2. ### 易读性与可维护性
    
    - **模块即命名空间**：前端或其他服务只需根据“模块名 + 操作名”调用对应 URL，无需关心实现细节。
        
    - **未来扩展**：如果某个模块拆分版本（如 `kb`），只需修改路由前缀至 `/v2/kb/...`，Controller 无需改动。
        
    

3. ### 逻辑层如何编写
    
    1. ####   统一基类
        
    
    - **ControllerBase：**所有 Controller 都继承自 `ControllerBase`，该基类提供：
        
        - **标准 CRUD** 方法：
            
            ```Python
            async def get(self, id: str)    → 返回 Python dict  
            async def list(self)           → 返回 Python dict（含分页、items 列表）  
            async def create(self)         → 返回 Python dict（刚创建的实体）  
            async def update(self)         → 返回 Python dict（更新后的实体）  
            async def delete(self, id: str)→ 返回 Python dict（包含被删除的 id）  
            ```
            
        - **键名转换**：驼峰 ↔ 下划线
            
        - **请求校验**：使用 Pydantic 对 `request.json` 进行验证
            
        - **业务异常封装**：抛出 `CustomMessageError` 或预定义错误码
            
    - **子类重写**
        
        - 若某个模块需要额外操作（如 `bulkImport`、`rebuildIndex`、`hybridSearch`），可以在子类 Controller 中新增对应的异步方法。
            
    
      
    
    2. ####   接口最外层捕获异常
        
    
    - 在 **Sanic 的 Exception Middleware**统一捕获所有异常，避免向前端抛出未处理的系统异常。
        
    - **JSON 返回格式**示例：
        
    
    ```JSON
    {
      "code": 1002,
      "msg": "知识库不存在",
      "data": null,
      "trace_id": "…可选，用于链路追踪…"
    }
    ```
    
    - 业务层若抛出 `CustomMessageError("xxx")`，路由层捕获后用 `code=非0、msg=错误内容` 返回。
        
    
    3. ####   业务异常分类
        
        - **CustomMessageError**
            
            - 用于封装可预期的业务逻辑错误（如“必填字段缺失”、“资源不存在”、“权限不足”等）。
                
            - 由 Controller 抛出，路由层捕获后直接把 `code`（可自定义）和 `msg` 返回给客户端。
                
        - **预定义错误码**
            
            - 如果有一系列可枚举的错误场景（如数据库操作异常），可以定义类似 `SQLError` 的错误类型，并在 `app.scheme.error_codes` 中对应该错误码与描述。
                
            - Controller 捕获后再抛出 `CustomMessageError`，路由层返回同一套 JSON 格式。
                
    
    4. ####   **系统异常**
        
        - 对任何未捕获的 Exception，路由层都当作“服务器内部错误”处理，`code` 统一设为 `500` 或自定义 `1000`（示例），并在日志里记录完整堆栈。
            
        - 返回示例：
            
            ```Markdown
            {
              "code": 1000,
              "msg": "服务器内部错误: 详细错误描述（避免泄露敏感信息）",
              "data": null
            }
            ```
            
    
    5. ####   日志记录
        
    
    - 在捕获异常的同时，调用 `logger.error(...)` 或 `logger.warning(...)`，记录：
        
        - `message_id` 放在请求上下文中，用于记录日志
            
        - 请求上下文（如 `request.json`，但敏感信息需脱敏）
            
        - 当前用户 ID（`request.ctx.user_id`，如可用）
            
        - 完整异常堆栈（对系统异常）
            
    - **避免敏感信息**：日志中不要打印明文密码、Token、完整堆栈（只在 `error` 级别写入，但不输出到前端）。

## 五、数据结构解析模块独立

### 1. 统一返回模型

- **Controller 返回“Python Dict”**
    
    - Controller 只负责把业务结果以 Python 字典或列表的形式返回，比如：
        
    
    ```JSON
    {
      "items": [ { "id": "kb1", "name": "示例" }, … ],
      "total": 100,
      "page": 1,
      "pageSize": 10
    }
    ```
    
- **Service 层统一包装**
    
    - 路由层接收 Controller 返回的 Python 对象后，再包装为以下统一格式：
        
    
    ```JSON
    {
      "code": 0,
      "msg": "success",
      "data": { …Controller 返回的字典… },
      "trace_id": "可选"
    }
    ```
    
    - 返回 Content-Type 始终为 `application/json`。
        

### 2. JSON 解析与校验

- **请求参数校验**
    
    - 采用 Pydantic 定义每个操作的请求模型，例如：
        
    
    ```Python
    from pydantic import BaseModel, Field
    
    class GetKbRequestModel(BaseModel):
        id: str = Field(..., description="知识库 ID，不可为空")
    
    class ListKbRequestModel(BaseModel):
        page: int = Field(1, ge=1, description="页码，最小为 1")
        pageSize: int = Field(10, ge=1, le=100, description="每页数量，1～100")
        filters: dict = Field(default_factory=dict, description="过滤条件，键值对格式")
        orderBy: str = Field(None, description="排序字段，驼峰命名")
    ```
    
    - 在scheme里面定义输入输出的数据结构。
        
        - 当批量操作时，需要返回批量数据的结果（哪些成功，哪些失败，参考 ItemOperationResponse）
            
        - 无需批量操作的话直接返回ORM对象的dict（参考FileController）
            
        
          
        
- 路由层使用 Sanic-Ext 的 `@validate(json=…)` 自动校验或者直接使用pydantic（**建议直接使用pydantic**，sanic-ext就是包了一层，底层还是pydantic），如不通过自动返回错误。
    
- **键名转换**
    
    - Pydantic 验证后得到的是“驼峰命名”字段，common_sdk基类里提供 `convert_dict_to_snake` 将其转换为下划线字段便于 ORM 操作；返回给前端时再转回驼峰（**这里已经与前端商量好，数据库为了保证兼容性，继续使用下划线字段，但是返回到前端需要转为驼峰**）。
        

### 3. Protobuf 预留（暂时不引入）

- **暂不引入 ProtobufOverHTTP**
    
    - 目前所有路由只接收 JSON → Controller → JSON 返回。
        
    - 但是设计时已预留“Content-Type 区分”与“反序列化／序列化”步，只需后续在同一路由加分支即可。
        
- **目录结构示例**
    

```Markdown
schema/
  ├── http/  
  │   
  ├── response.py   # JSON 场景下的通用返回模型（Pydantic BaseResponse、错误码等）
  │   ├── kb_models.py  # GetKbRequestModel, ListKbRequestModel, CreateKbRequestModel…
  │   └── errors.py     # 错误码与错误消息定义
  └── protobuf/         # 后续如果要加 Protobuf，可以把 .proto 放在这里
      ├── kb.proto
      ├── policy.proto
      └── user.proto
```

## 六、按版本号进行分层（可选）

1. **为什么要分层**
    
    1. 随着产品演进，业务接口可能发生向后兼容或向前兼容的变动。通过按版本号（如 v1、v2）进行分层，可以在不中断老客户端调用的情况下，对新功能或重构后的接口进行迭代。
        
2. **实现方式**
    
    1. **HTTP 路由示例**
        
    
    ```Bash
    /api/v1/kb/create
    /api/v1/kb/get/{id}
    /api/v2/kb/create   # v2 新增字段或优化逻辑
    /api/v2/kb/get/{id}
    ```
    
3. **注意事项**
    
    1. 在版本迭代时，保持文档与代码同步。
        
    2. 定期清理已废弃的旧版本接口，但需提前向合作方（甚至外部客户）公告迁移计划。

## 📦 六、依赖管理规范

### 依赖包管理与安装流程

**固定依赖包版本，写入** **`pyproject.toml`****：** 使用 **Poetry** 管理项目依赖，所有包的版本固定在 `pyproject.toml` 文件中，示例内容如下：

```Markdown
[tool.poetry.dependencies]
python = "^3.11"
sanic = "23.12.1"
asyncpg = "0.29.0"
tortoise-orm = "0.20.0"
pydantic = "2.5.3"
```

1. **SDK 依赖包单独管理：**
    
    1. 如果需要修改 **`ai_sdk`** 或 **`common_sdk`** 中的依赖，请分别在各自的 `pyproject.toml` 文件中进行修改。具体操作方式如下：
        
        - 在 **`ai_sdk`** 下的 `pyproject.toml` 修改其依赖。
            
        - 在 **`common_sdk`** 下的 `pyproject.toml` 修改其依赖。
            
2. **安装命令：**
    
    1. 使用 **Poetry** 安装依赖包，命令如下：
        
    
    ```Markdown
    poetry install
    ```
    
    2. 这会根据 `pyproject.toml` 文件中的配置，自动安装所有的依赖。
        
3. **Dockerfile 配置：**
    
    1. **Dockerfile** 配置保持统一，唯一不同的是项目名称。其他配置无需修改。
        
    
    ```Bash
    # 推荐方案：Poetry 导出 + pip 安装
    
    # 第一阶段：使用 Poetry 导出完整的 requirements.txt
    FROM swr.cn-east-3.myhuaweicloud.com/ai-prd/python:3.11-slim AS req-generator
    
    # 设置 Debian 镜像源
    RUN sed -i 's/deb.debian.org/mirrors.ustc.edu.cn/g' /etc/apt/sources.list.d/debian.sources || \
        sed -i 's/deb.debian.org/mirrors.ustc.edu.cn/g' /etc/apt/sources.list
    
    # 设置 PYPI 镜像
    ARG PYPI_URL=https://pypi.tuna.tsinghua.edu.cn/simple
    ARG PYPI_TRUSTED=pypi.tuna.tsinghua.edu.cn
    
    # Poetry 环境变量
    ENV POETRY_NO_INTERACTION=1 \
        POETRY_VENV_IN_PROJECT=1 \
        POETRY_CACHE_DIR=/tmp/poetry_cache
    
    # 安装 Poetry
    RUN pip config set global.index-url ${PYPI_URL} && \
        pip config set install.trusted-host ${PYPI_TRUSTED} && \
        python -m pip install --no-cache-dir -U pip && \
        pip install --no-cache-dir poetry==2.0.0 poetry-plugin-export==1.9.0
    
    # 配置 Poetry
    RUN poetry config virtualenvs.create false
    
    WORKDIR /app
    COPY pyproject.toml poetry.lock* ./
    
    # 导出包含所有依赖组的 requirements.txt
    RUN poetry export \
        --with ai-sdk,common-sdk \
        --format requirements.txt \
        --output requirements.txt \
        --without-hashes \
        --verbose
    
    # 验证导出结果
    RUN echo "=== 导出验证 ===" && \
        echo "总依赖数量: $(wc -l < requirements.txt)" && \
        echo "关键依赖检查:" && \
        grep -E "(langchain|pymilvus|aiohttp|openai|httpx)" requirements.txt | head -5 || echo "某些关键依赖可能缺失"
    
    # 第二阶段：使用 pip 安装依赖（更轻量的运行时镜像）
    FROM swr.cn-east-3.myhuaweicloud.com/ai-prd/python:3.11-slim AS runtime
    
    # 设置 Debian 镜像源
    RUN sed -i 's/deb.debian.org/mirrors.ustc.edu.cn/g' /etc/apt/sources.list.d/debian.sources || \
        sed -i 's/deb.debian.org/mirrors.ustc.edu.cn/g' /etc/apt/sources.list
    
    # 环境变量设置
    ENV API_VERSION=v1.0 \
        PYTHONDONTWRITEBYTECODE=1 \
        PYTHONUNBUFFERED=1 \
        PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION="python" \
        TZ=Asia/Shanghai
    
    # 设置 PYPI 镜像
    ARG PYPI_URL=https://pypi.tuna.tsinghua.edu.cn/simple
    ARG PYPI_TRUSTED=pypi.tuna.tsinghua.edu.cn
    
    # 设置时区
    RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
    
    # 安装编译依赖（某些 Python 包需要）
    RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential \
        && rm -rf /var/lib/apt/lists/*
    
    WORKDIR /app
    
    # 复制生成的 requirements.txt
    COPY --from=req-generator /app/requirements.txt ./
    
    # 配置 pip 并安装所有依赖
    RUN pip config set global.index-url ${PYPI_URL} && \
        pip config set install.trusted-host ${PYPI_TRUSTED} && \
        python -m pip install --no-cache-dir -U pip && \
        pip install --no-cache-dir -r requirements.txt
    
    # 复制应用代码
    COPY . .
    
    # 创建非 root 用户
    RUN adduser -u 5678 --disabled-password --gecos "" appuser && \
        chown -R appuser /app
    
    USER appuser
    
    # 启动命令
    CMD ["gunicorn", "-c", "config.py", "main:app"]
    ```
