## 业务背景



随着公司电商业务向天猫、京东、亚马逊、淘宝、抖音等全渠道渗透，商品资产的合规性与价格稳定性面临巨大挑战。

#### 核心痛点

|  痛点 | 问题描述  | 影响 |
|-|-|-|
| 反爬机制升级 | 主流电商平台通过登录墙、图形验证码及设备指纹追踪，使得传统固定爬虫脚本频繁失效 | 维护成本极高 |
| 人工监控滞后 | 依赖人工手动刷新页面检查价格违规或图片侵权，效率低下 | 无法 7×24 小时实时预警  |
| 异常链路断裂 | 自动化脚本遇到扫码登录或滑块验证时程序直接中断 |  缺乏人机协同闭环 |

| 工具 | 优点 | 缺点 | 结论 |
|-|-|-|-|

| AgentBay | 云浏览器、指纹隔离、可配置化、VNC 实时观测 | 需要学习 SDK | ✅ 采用 |

### 5.3 内部模块说明

#### AccountPool（账号池管理）

```Python
class AccountPool:
    """
    账号池管理，按平台分组
    - 每个账号只属于一个平台
    - Redis 存储账号状态和 Cookie
    """
    
    async def get_available(self, platform: str) -> Account:
        """获取该平台一个可用账号"""
        
    async def mark_blocked(self, account_id: str):
        """标记账号被封"""
        
    async def mark_login_expired(self, account_id: str):
        """标记登录态过期"""
```

```Plain Text

account:status:{account_id}  → Hash {status, last_used, login_expires}
account:cookie:{account_id}  → String (加密 Cookie)
```

####   
RetryPolicy（重试策略）

```Plain Text
class RetryPolicy:
    """自动切换账号重试"""
    
    async def execute_with_retry(
        self, 
        platform: str, 
        action: Callable,
        max_retries: int = 3
    ):
        for i in range(max_retries):
            account = await self.pool.get_available(platform)
            try:
                return await action(account)
            except CaptchaError:
                # 需要人工，返回给 Agent
                return {"status": "captcha_required", ...}
            except (BlockError, TimeoutError):
                # 切换账号重试
                await self.pool.mark_blocked(account.id)
                continue
        
        return {"status": "all_accounts_failed"}

```

  
性能：  
\- 切换账号：1-2ms（Redis 操作）  
\- 重新登录：2-5s（仅过期时触发）  
\- 后台预刷新(可以不做)：过期前 10 分钟自动刷新

#####  一、账号与生命周期管理

###### 1.资源池化模型

我们将账号、环境（指纹）、代理 IP 视为三个独立的资源池，通过**调度引擎**进行动态组合。

- **账号池 (Account Pool)**：存储 JD/TB 账号凭证、所属平台、当前状态。
- **环境池 (Instance Pool)**：AgentBay 的 Profile ID（指纹环境），负责提供浏览器底座。
- **账号状态机**：

  - **Available**：空闲且登录态有效。
  - **Busy**：执行中。
  - **Cooling**：触发风控或访问过频，进入冷却期（如 2 小时后解封）。
  - **Expired**：Session 失效，需重新登录。
- **动态组合机制**：

  - **正常态**：`账号 A` + `环境 A` + `代理 A` 执行任务。
  - **故障态**：若 `账号 A` 报错（如被平台限制），调度引擎立即释放 `环境 A`，从账号池抓取 `账号 B` 注入到 `环境 A`（或新的 `环境 B`）中继续抓取。

###### 2.登录态管理

**登录态保存**：

- **提取 Cookie**：登录成功后，脚本通过 API 提取关键 `Cookie` 和 `LocalStorage` 数据，加密后存入数据库（关联到 `账号 ID`）。
- **长效保持**：定期执行“保活脚本”（如自动点击“我的订单”），防止 Cookie 过期。

**动态注入执行**：

- 当需要使用 `账号 B` 时，启动一个新的 AgentBay 实例，通过代码动态 `addCookies` 将 `账号 B` 的登录态注入浏览器，直接实现“免密登录”。

**登录失败/失效兜底**：

- **自动重试**：若注入后发现登录态失效，触发“自动登录流”（帐密+接码）。
- **换号重洗**：若自动登录失败（需扫码且无人值守），立即将该账号标记为 `Pending`，从池中换一个 `Active` 账号继续任务，确保**接口响应不中断**。
- **VNC 离线补录**：当账号池整体存活率低于 30% 时或其他账号已全部在使用中时，触发飞书告警，管理员通过 VNC 远程批量扫码维护。

##### 二、抓取与异常处理

###### 1. 抓取闭环逻辑

1. **分流执行**：根据账号所属平台分配对应的执行任务（session）。
2. **验证码阻断 (VNC Over Tool)**：遇到验证码时，session 挂起并向管理后台发送 `Auth_Request`。
3. **人工接管接口**：在飞书端推送 VNC 实时镜像。管理员操作完成后，点击“已解决”，RPA 接收信号通过 `resume()` 继续执行，同时系统**自动同步最新 Cookie 到数据库**，供后续任务动态注入使用。
4. **数据落库**：记录抓取的链接、平台、结果、当前时间、执行结果

###### 2. 失败兜底与重试机制

- **软失败 (Soft Fail)**：网络抖动或元素未加载。策略：**原账号原环境原地重试 (Max 3次)**。
- **硬失败 (Hard Fail)**：账号被弹窗拉黑或 IP 被封。策略：**触发账号下线飞书告警 -> 切换备用账号池 -> 记录该指纹环境异常日志**。

#####  三、通讯协议与幂等性设计

###### **1.接口协议：异步 Task-Queue 模式**

由于爬虫任务耗时长（秒级到分钟级），禁止使用同步 HTTP 阻塞请求，统一采用 **RESTful API + MQ (如 Redis/RabbitMQ)**。

- **请求示例**： `POST /v1/task/inspect`
- JSON

```Plain Text
{
  "request_id": "UUID-123456", // 幂等 Key
  "platform": "Tmall",
  "target_url": "https://detail.tmall.com/...",
  "strategy": "daily_check"
}
```

######  2. 幂等性保障

- **ID 唯一约束**：

  - 服务端收到请求后，先检查Redis中的 `task_status:{request_id}`。若状态为 `PROCESSING`，直接返回“已在执行中”；若为 `SUCCESS`，跳过执行。
  - 第一次执行时，处理前先在 Redis 设置 `SET NX`（过期时间 10 分钟）。
- **执行锁**：在 RPA 执行层，对 `Account_ID` 加分布式锁。确保同一时间一个账号只被一个session 进程占用，防止多地登录触发风控。

##### 二、技术架构

- 采集层：AgentBay 浏览器自动化
- 调度集成层：Sanic  +  Pydantic
- 分析层：

  - 文本：Aho-Corasick 规则引擎
  - 视觉：Qwen-VL 多模态大模型
  - 价格：自研规则引擎 + 历史价格验证
- 存储层：飞书多维表格（业务） + pgsql（分析）
- 协同层：飞书卡片

##### 三、核心模型与算法

**文本合规检查：Aho-Corasick 自动机**

- 输入：商品标题、主图文案
- 词库：200+ 广告法禁用词（支持从飞书多维表动态更新）
- 输出：违规词列表
- 性能：10万字/秒，内存 < 50MB
- 优势：比正则/循环快 10 倍，适合高并发场景

**视觉安全分析：Qwen-VL-Plus（阿里云百炼）**

- 输入：详情页图片 URL
- Prompt：

> - “请严格检查此电商图片是否包含：1. 医疗宣称（如‘根治’）2. 绝对化用语 3. 竞品 Logo。返回 JSON：{status, type, detail}”

- 输出：结构化风险描述
- 调用方式：DashScope HTTP API（无需本地部署）

**价格真实性校验：规则引擎 + 历史验证（例）具体规则待反馈**

- 规则1：`final_price = current_price - coupon`
- 规则2：`final_price >= channel_min_price`（从飞表读取）
- 规则3：若 `discount < 0.5`，则调用历史价格 API 验证原价真实性
- 兜底：无历史数据时，标记为“高风险”
