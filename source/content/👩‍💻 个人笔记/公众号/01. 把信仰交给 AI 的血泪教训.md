##  🎯 demo完美，上线总是失败？

别管什么高大上的模型，你的 Agent 失败，99% 是因为下面这五个工程问题。

### 1. 崩坏一：价值观失控，触碰“信仰红线”

这是最严重的崩坏。当 Agent 涉及到**宗教、政治、或极端观点**时，一次回答错误就能让你项目直接死亡。

#### 故事：Agent 在宗教咨询中“越界”

在我们的**信仰咨询 Agent**项目中，我们发现，LLM（大语言模型）的“普世价值观”和**特定信仰社群**的**核心教义**是冲突的。

有一次，用户提问了一个关于教义中“牺牲”的解读。Agent 试图用世俗的、理性化的语言去解释，结果给出的答案 **直接违背了教派的核心教义**，引发了社区的强烈不满。

#### 反思：为什么会越界？

问题不在于模型笨，而在于 **边界没有被代码写死**。你只是在 Prompt 里说“你要专业”，但没告诉它 **“什么话绝对不能说”**。

> **直白点：** Agent 是个外行，你必须给它一张 **禁区地图**。

#### 修复方案：双层白名单与“不答”策略

我们把风险管理前置到 LLM 决策之前，确保它在禁区外活动。

**核心修复方案：
1. ** 建立 **信仰/敏感策略白名单**（明确什么话题不能碰）；
2. 设计 **意图→工具白名单**（明确什么权限不能用）；
3. 搭配 **“拒答/澄清/转人工”** 的三段式兜底。

### 2. 崩坏二：工具不幂等与购物车状态混乱

这是直接损害用户利益的崩坏，发生在**订餐、支付、购票**等交易场景。

#### 故事：订餐 Agent 两次创建订单和购物车混乱

在我们**订餐 Agent** 的落地中，有两个问题最致命：

1. **重复创建订单（未支付）：** 网络抖动导致 Agent 重试，虽然没有直接扣费，但系统后台生成了 **两个一模一样的待支付订单**。用户不知道点哪个链接，最后选择了其中一个支付，另一个订单资源（如优惠券、库存）被白白占用。
    
2. **购物车状态不一致：** 用户在对话中修改了数量（如加一份小吃），但 Agent 调用库存校验服务时，价格服务算出的总价还是旧的，导致 **用户看到的最终价格和服务间的状态不一致**。
    

> **当时的感受：** 比扣费更隐蔽的风险是 **资源污染** 和 **用户选择困难症**。

#### 为什么会多创建订单？

根本原因：**工具调用不幂等**（没有唯一ID），以及 **Agent 越权**（试图在一次对话中完成所有事务）。 Agent 的核心价值是 **构建** 订单，而不是 **支付** 订单。

> **直白点：** Agent 的任务是 **“把菜配好，把价格算清，生成一个结账码”**，它不能替用户按 **“确认付款”** 键。

#### 修复方案：幂等键 + 订单原子化 + 补偿链

我们把任务的事务性看得比模型的“聪明”程度更重要，并让 Agent 止步于安全边界。

**核心修复：** 
1. 以 **会话任务 ID** 做幂等键；
2. **价格计算** 和 **库存校验** 必须前置为原子服务，输出 **快照**，确保购物车数据一致性；
3. 最终输出应为 **“待支付订单ID/链接”**，而非直接扣费。

### 3. 多轮对话后总是“失忆”！

这是一个效率低下的崩坏。Agent 无法完成复杂、多步骤的任务。

#### 故事：Agent 在流程中途“变傻”

在客服 Agent 中，用户聊了三四轮后，系统突然忘记了第一轮的约定，开始胡言乱语。我们发现，问题出在 **流程控制全靠 LLM 的“感觉”**。

#### 反思：为什么会失忆？

深层原因：缺乏 **显式节点图**。你把复杂的业务流程（如：询价 $\to$ 确认 $\to$ 支付）扔给 LLM **隐式记忆**，一旦 Context Window 压力大，它就“人格分裂”了。

> **直白点：** 别相信 Agent 的记忆力，你必须给它一个 **清晰的地图和步骤**。

#### 修复方案：显式节点图与阶段机

把 Agent 的任务流程画成图，严格控制每一步能做什么。

**核心修复：**
1. 把任务画成 **显式节点图**；
2. 采用 **阶段机** 限制节点可用工具和流程走向（规定前置/可重试/回退条件）。
3. 不是很建议大家将太多时间花在研究记忆压缩等技术上面，分而治之往往是最具有性价比的解决方法。

### 4. 知识库污染，Agent 开始“编故事”

这是最常见的信任崩坏。Agent 引用了错误或过期的数据。

#### 故事：引用了过期的“祖传”流程

企业问答 Agent 在回答 IT 流程时，引用了 **三年前的过期文档**，导致员工操作失误。同时，在解析复杂合同或政策时，RAG 检索只命中了一小部分文本（Chunk 粒度不当），使得 Agent 在信息不全的情况下 **“自信地胡说”**。

#### 反思：为什么会编故事？

根本原因：**知识缺乏版本控制与权威性校验**，以及 **RAG 缺乏自我校对机制**。简单的 RAG 是“单向”的，它拿到什么就信什么，无法判断检索到的信息是否足够、是否权威。

> **直白点：** 知识库就像一个没整理的书架，Agent 只是个学徒，它不知道哪个版本是**最新法律**，也没有一个 **“自我检查”** 的习惯。

#### 修复方案：数据分层 + 反思型 RAG（验证链 CoVe）

我们引入 **反思机制**，让 Agent 在回答前多问自己一句：“我引用的证据准确吗？”

**核心修复：**

1. **数据分层隔离：** 文档分层（生产库/沙盒库/过期库），确保知识来源的权威性。
    
2. **结构化检索：** 采用 **结构化索引**（章节/定义/例外）+ **混合召回**，提高证据的精准度。
    
3. **反思型 RAG/验证链 (CoVe)：** Agent 生成初稿后，强制进行 **二次核对**，验证关键句是否真的来自证据段落。

### 5. 崩坏五：观测缺失，出了问题全靠“蒙”

这是一个无法优化的崩坏。你根本不知道 Agent 为什么失败。

#### 故事：定位 Bug 全靠“猜”

系统出现问题时，我们无法确定是 **意图识别错了**、**RAG 检索错了**、还是 **工具调用失败了**。缺乏数据，所有优化都是盲目调整 Prompt。

#### 反思：为什么只能“感觉”？

深层原因：只关注了 **结果（黑盒）**，没有关注 **内部事件流（白盒）**。

> **直白点：** 别只看 Agent 的嘴（最终回答），要看它的 **脑子（意图）**、**眼睛（检索）** 和 **手（工具）** 做了什么。

#### 修复方案：四类埋点 + “4+1”核心指标

建立一套完整的 Agent 观测体系。

**核心修复：** 
1. 四类埋点（**意图/检索/工具/回复**）；
2. **“4+1”指标**（成功率、P95 延时、成本/任务 CPT、误导率 Hallucination、用户步骤 User Steps）。

## II. 🛠️ 落地框架：从“Demo”走向“生产力”

这个框架是我用两年时间总结的，可直接套用。

|**阶段**|**核心目标**|**直白点说（要做什么）**|
|---|---|---|
|**SLA 定义**|避免目标错位|**写死** 成功率阈值。失败了，怎么 **降级**（是转人工还是直接拒答）。|
|**意图与权限**|明确 Agent 边界|告诉 Agent **它能干什么**（工具清单），**它不能干什么**（敏感白名单）。|
|**工具与事务**|保证交易不出错|给每次交易一个 **唯一 ID**（幂等键），保证扣钱只扣一次。|
|**知识与版本**|保证知识权威性|文档必须 **分层**（生产/过期），上线前用 **对抗集** 测一遍。|
|**观测与评测**|出了问题能定位|埋点记录 Agent 的 **思考过程**，而不是只看最终结果。|
|**灰度与回滚**|保证上线稳定|小范围试用（门店/人群），指标破线 **自动退回旧版本**。|

## III. ✅ 上线前的“低成本正确性”清单（必做）

在你的 Agent 上线前，请务必对着这份清单进行自检。

- **对抗样例：** 每个关键意图配 **10 条对抗样例**（方言、口误、歧义、脏话）。
- **工具重放：** 所有工具调用必须实现 **可重放机制**（请求/回包脱敏落盘）。
- **事故演练：** 随机注入 **5% 工具失败**，检验 **补偿闭环** 是否有效。
- **看板极简化：** 看板只放 **成功率、P95、CPT、误导率** 这四个核心指标。
- **兜底明确：** **拒答/澄清/人工** 兜底路径必须明确且可触发。
