# 四、要融合的方案

## 4.1 飞书接入层：团队目录自动选择 Profile

这里不是手动按场景切 profile，而是已经做成了 PATH 级自动分流：shell、脚本和数字员工只要在团队目录里调用 `lark-cli`，会先命中 `~/.local/bin/lark-cli` wrapper，由 wrapper 自动读取最近的团队 `.env`，再把对应 profile 注入真实 CLI。

**真实调用链路：**在团队目录执行 `lark-cli` → PATH 命中 `~/.local/bin/lark-cli` → wrapper 用 `pwd -P` 向上查找最近的 `.env` → 读取 `LARK_CLI_PROFILE`、`LARK_CLI_BRAND` 和应用配置 → 调用真实 `~/.npm-global/bin/lark-cli` 并自动注入 `--profile`。

**Profile 的作用：**profile 和团队目录绑定，用来隔离不同团队的飞书应用、账号授权和写回空间。active profile 不是关键，关键是 wrapper 会按当前目录自动解析并注入正确 profile。

**业务效果：**不同部门可以共用 Hermit 的工作台和能力库，但飞书侧读写会落到各自团队的 profile 与权限边界里；脚本、Skills、Workflow、Cron 也能沿用同一套自动分流机制。

## 4.2 融合范围：把已有能力接入同一个工作台

这里的“融合”不是重新做一套系统，而是把各团队已经跑出来的能力资产接到平台：团队入口、任务现场、文件与证据、Skills、MCP/连接器、Workflow 和定时巡检统一在一个数字员工工作台里管理。

**已具备的能力资产：**经营看板与管理报告、客服 VOC 与知识检索、跨境电商与渠道运营、产品研发与结构评审、采购寻源与供应链履约、财务工时与成本分析、专利 IP 与技术情报、用户研究/设计/营销内容生产、组织治理与团队资产运营。

**融合后的分工：**Skills 负责把业务动作标准化，MCP/连接器负责接入飞书、多维表格、BOM、知识库、VOC、项目、专利和电商等系统，Workflow 负责把多步骤任务串成闭环，Cron/定时负责日报、巡检、提醒、报告刷新和异常发现。

**对业务的好处：**每个部门不用从零搭建 AI 助手；已有脚本、看板、文档、流程和连接器可以沉淀为可复用能力，下一个团队只需要按说明书接入、验证、复制。

融合方案的核心不是“功能越多越好”，而是把工作台、飞书连接、团队说明书、任务巡检和证据沉淀连成一条业务链。

# 六、希望的产品方向：去中心化单机部署

hermit 以后走去中心化的单机部署路线。企业、部门、个人都能用，但不是靠一个中心系统调度所有人，而是每个团队目录、每台机器都能独立运行。

每个人、每个部门都能在自己的机器上跑；跑通以后，把说明书、连接器、Workflow、定时任务和证据模板打成能力包。以后换机器、换团队目录，就导入这个包继续用。Hermit 只管运行时切换、结果证据和能力包导入 / 导出

暂时无法在SKG-飞书文档外展示此内容

**不做多团队自动协作：**跨团队分发任务、自动协同不是当前真需求。

**不做权限管理平台：**权限边界交给飞书、系统账号和本地 profile 机制；hermit 不变成一套新的权限系统。
