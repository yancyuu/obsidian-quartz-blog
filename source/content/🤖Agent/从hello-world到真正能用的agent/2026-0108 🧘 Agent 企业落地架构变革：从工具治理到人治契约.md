### 引言：对架构演进的再思考

在之前的认知中（如《[2025-0415 🍖构建可演化的智能体系统架构](2025-0415%20🍖构建可演化的智能体系统架构.md)》），我曾认为 MCP 和 A2A (Agent-to-Agent) 并非企业落地的必要条件。在探索期或 MVP 验证阶段，**一体式工具架构（Monolithic Tooling）** 确实可行且高效。

但随着企业落地的深入，我发现除了技术本身的挑战（如幻觉、测试），更大的痛点在于**业务边界的不明确**。

> **核心洞察：** 企业引进 MCP 是非常有必要的。不仅仅是为了技术解耦，更是为了**“人治”**。 MCP 协议是一套通用的“契约”，它强制划分了业务和组织的边界。在企业架构中，设计模式的解耦能力，本质上是组织治理能力的体现。


### 一、 企业落地 Agent 应用的两大路径
#### 1. 全新开发 (Greenfield)

从零开始，为一个全新的业务场景或颠覆性的产品构想，原生设计和开发 AI 应用（如企业内部的“超级知识入口”）。
- **优势：** 不受历史债务束缚，可直接采用最先进的 **AI Native** 架构。

#### 2. 存量改造 (Legacy Modernization) —— **变革的主战场**

这是绝大多数企业选择的路径：在成熟的核心业务系统（ERP、CRM、IAM）中嵌入 AI Agent 能力。

- **价值：** 直接作用于核心流程，价值释放路径短。
- **挑战：** 面对无接口的黑盒系统。
- **解法：** 采用**“双模执行架构”**（可控+可伸缩+解耦）：
    - **API 通道：** 对接现代化系统（快模式）。
    - **RPA 通道 (Agentbay)：** 利用容器化的 **Agentbay** 结合 **LVM (视觉模型)**，对老旧系统进行非侵入式操作（慢模式/异步）。

### 二、 AI 应用架构新范式

![](images/2026-0108%20🧘%20Agent%20企业落地架构变革：从工具治理到人治契约/file-20260108121540023.png)
#### 1. AI 网关 (AI Gateway)：收敛模型能力，而非工具
**定义：** AI 网关是企业所有 Agent 访问模型服务（LLM/LVM/ASR）的唯一出口。 
**演进策略：**
- **MVP 阶段（下沉至 Runtime 层）：** Agent Runtime 直接配置 OpenAI/DeepSeek 的 API Key，点对点调用。
- **企业级阶段（网关/注册中心介入）：** 必须引入 AI 网关（如 Higress/Zuplo/自研）。
    - **统一管控：** 屏蔽底层模型差异（OpenAI 挂了自动切 Azure，或者切国产模型），实现**模型路由**。
    - **三类角色协同：**
        - **开发者：** 申请 Token，调试 Prompt。
        - **管理者：** 限制各部门 Token 额度，配置计费策略（Cost Management）。
        - **安全员：** 过滤进出模型的敏感词（DLP），防止数据泄露。

#### 2. MSE Nacos + MCP Registry：统一管理工具资源
**定义：** 既然 Runtime 下沉了，我们靠什么来避免“工具孤岛”？靠**注册中心**。
- **MSE Nacos 的新使命：** 不仅注册传统的微服务（API），更要增加 **MCP Registry** 能力。
- **现存业务 0 改造：**
    - 企业现有的几百个 Java 微服务，不需要改代码。
    - 通过 Nacos 的元数据映射，将它们在 Agent 视角里“伪装”成 MCP 服务。
    - Runtime 启动时，向 Nacos 询问：“我是财务 Agent，请给我拉取所有财务域的工具列表（包含 MCP 和 API）。

#### 3. Agent 组件铁三角：明确职责边界
- **Agent 编排框架 (Brain)：** 负责 Prompt 模板管理和记忆路由。
- **Agent 运行时 (Runtime)：** **下沉的核心**。
    - 它左手握着 **MCP/API Client**（通过 Nacos 发现工具，直接调用）。
    - 它右手握着 **Model Client**（通过 AI 网关调用模型）。
    - 它直接负责执行的“快慢双模”（API 直连 or Agentbay RPA）。
- **Agent 观测平台 (Observability)：** 监控“Token 消耗（来自 AI 网关）”和“工具执行结果（来自 Runtime）”的全链路数据。

#### 4. 计算环境选型：FC vs K8s (决策矩阵)

**FC (阿里云函数计算)** 具备丰富的触发器，完美适配 AI Agent 的事件驱动特性，天然适合作为 **Agent Sandbox**。
**决策建议：**
- **推荐方案（图简单/验证期）：** 直接用 **阿里云 FC**。
- **进阶方案（图自主/成本优化）：** 若需内控或成本优化，使用 **K8s + Knative**。

> **什么时候选 FC？**
> 
> - 业务不确定，流量波动大，爆发式增长或长时间低负载（Scale-to-Zero）。
> - 想快速验证 / 快速迭代，团队人手有限。
> - 以事件驱动为主（HTTP、队列、对象存储触发等）。
> - 需要较强的“沙箱”隔离但不想自建底层。


> **什么时候选 K8s？**
> - 有**强合规/内网**要求（如必须在专有网络、专有集群，数据不出域）。
> - **稳定高负载**、长期运行的服务（如 24 小时运行的监控 Agent），优化单位算力成本。
> - 需要深度自定义：特殊调度（GPU/MIG 用于部署私有 LVM）、自定义网络/网关。
> - 已有成熟容器平台团队。

### 做AI开发的人员画像：
技术：
1. Agent编排能力边界模糊，控制面市面上框架很多，企业版本的控制面最好放后端，好对接企业自身的鉴权服务。放前端等于白给，技术栈基于python的生态会更好一些，Java也可以。
2. 最好有一定的AI应用开发经验，具备一定的上下文优化能力（rag，function-call，prompt，mcp等）。
3. AI应用多为io密集型应用，要求人员有比较强的异步编程能力。

软能力：
1. 会主动使用各种AI工具，有比较强的好奇心。
2. 具备较高认知，无过强的路径依赖，善于合作和倾听。
3. 最好有交叉学科背景。
