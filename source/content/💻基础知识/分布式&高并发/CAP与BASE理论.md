# CAP 与 BASE 理论

> 分布式系统的**奠基理论**，面试几乎必问：「CAP 是什么？为什么只能三选二？BASE 又是什么？」搞不懂这两个，分布式面试寸步难行。

## 一、CAP 定理

分布式系统在**网络分区（P）发生时**，只能在 **C（一致性）** 和 **A（可用性）** 之间二选一：

| 字母                                    | 含义                                                       |
| --------------------------------------- | ---------------------------------------------------------- |
| **C - Consistency（一致性）**           | 所有节点**同一时刻**看到相同数据（读总能读到最新写）       |
| **A - Availability（可用性）**          | 系统一直可用，每个请求都能收到**非错误**响应（不保证最新） |
| **P - Partition tolerance（分区容错）** | 网络**分区**（节点间通信失败）时系统仍能运作               |

### 为什么是三选二（其实是 CP vs AP）

> P 在分布式系统**必然存在**（网络不可能 100% 可靠），所以实际选择是 **CP 还是 AP**。

```mermaid
flowchart TD
    P[网络分区发生] --> Q{如何抉择}
    Q -->|CP| C[拒绝服务以保证一致<br/>如 ZooKeeper/etcd/Redis(主写)]
    Q -->|AP| A[继续服务允许短暂不一致<br/>如 Eureka/Cassandra/Redis Cluster]
    style C fill:#dbeafe
    style A fill:#dcfce7
```

### CP vs AP 选型

| 选择   | 牺牲谁                       | 特点             | 典型                                            |
| ------ | ---------------------------- | ---------------- | ----------------------------------------------- |
| **CP** | 可用性（分区时部分请求失败） | 强一致           | **ZooKeeper / etcd** / HBase / 多数关系型DB     |
| **AP** | 强一致（允许短暂不一致）     | 高可用、最终一致 | **Eureka / Cassandra / Redis Cluster** / Dynamo |

> CA（舍弃P）只在单机系统成立（无网络分区问题），分布式必然带 P。

## 二、BASE 理论（CAP 的工程实践）

CAP 中选 AP 的系统，如何兼顾一致性？**BASE** 是对 AP 的补充——**追求最终一致性**：

| 字母                                        | 含义                                                     |
| ------------------------------------------- | -------------------------------------------------------- |
| **BA - Basically Available（基本可用）**    | 故障时**损失部分可用性**保核心（如降级、响应变慢、限流） |
| **S - Soft state（软状态）**                | 允许数据存在**中间状态**（副本不一致），不要求时刻强一致 |
| **E - Eventually consistent（最终一致性）** | 副本经过一段时间同步后**最终达成一致**                   |

> BASE = 「牺牲强一致，换可用性 + 最终一致」。互联网大规模系统（电商、社交）几乎都是 AP + BASE。

### 最终一致性的几种变体

| 类型           | 说明                   | 例子                         |
| -------------- | ---------------------- | ---------------------------- |
| **读己之写**   | 自己写的自己立刻能读到 | 主从异步复制下不保证，需读主 |
| **单调读**     | 后读不会看到更旧的值   | 同一用户固定读某副本         |
| **因果一致性** | 有因果关系的写顺序一致 | 评论 → 点赞                  |

## 三、强一致 vs 最终一致（决策）

```mermaid
flowchart TD
    Q{业务对一致性要求?}
    Q -->|强一致(金融/库存核心)| S[CP + 强一致<br/>2PC/分布式锁/同步复制]
    Q -->|最终一致可接受(社交/缓存/搜索)| E[AP + BASE<br/>异步复制/消息队列/补偿]
    style S fill:#fecaca
    style E fill:#dcfce7
```

> 不是所有场景都要强一致。**金融核心用 CP，社交/缓存/推荐用 AP+BASE**。

## 四、面试速答

> **Q：CAP 是什么？为什么三选二？**
> A：C 一致性、A 可用性、P 分区容错。P 在分布式必然存在，所以分区时只能在 CP（保一致牺牲可用，如 ZK）和 AP（保可用允许短暂不一致，如 Eureka）二选一。

> **Q：BASE 是什么？**
> A：基本可用、软状态、最终一致。是 AP 系统的工程实践——放弃强一致，换高可用 + 最终一致。大规模互联网系统多用 BASE。

> **Q：ZooKeeper 是 CP 还是 AP？Eureka 呢？**
> A：ZK 是 CP（leader 选举期间对外不可用，保证一致）；Eureka 是 AP（节点对等，任一可服务，允许短暂不一致）。

> **Q：强一致和最终一致怎么选？**
> A：金融/库存等核心场景要强一致（CP）；社交/缓存/搜索等容忍延迟的场景用最终一致（AP+BASE），可用性和性能更好。
