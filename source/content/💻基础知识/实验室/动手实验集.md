### 实验 1：GIL 的真相（⭐⭐⭐ 必做）

**知识点**：为什么 Python 多线程不能加速 CPU 密集任务

```python
# gil_truth.py
import time, threading, multiprocessing

COUNT = 80_000_000   # 要够大，否则进程启动开销 > 计算节省（会误判多进程更慢）
def cpu_heavy(n):
    while n > 0: n -= 1

def single():
    t = time.time(); cpu_heavy(COUNT); cpu_heavy(COUNT)
    print(f"单线程:  {time.time()-t:.2f}s")

def threaded():
    t = time.time()
    ts = [threading.Thread(target=cpu_heavy, args=(COUNT,)) for _ in range(2)]
    for x in ts: x.start()
    for x in ts: x.join()
    print(f"多线程:  {time.time()-t:.2f}s   ← ≈ 单线程！GIL 在捣鬼")

def multiproc():
    t = time.time()
    ps = [multiprocessing.Process(target=cpu_heavy, args=(COUNT,)) for _ in range(2)]
    for x in ps: x.start()
    for x in ps: x.join()
    print(f"多进程:  {time.time()-t:.2f}s   ← 快一倍！真并行")

# ⚠️ macOS/Windows 必须有 __main__ 保护（默认 spawn 启动进程，否则报错）
if __name__ == '__main__':
    single(); threaded(); multiproc()
```

**实测输出**：`单线程 3.31s / 多线程 3.21s / 多进程 1.75s` —— 多线程白搭、多进程真提速。

**形象时序图（为什么）**：


GIL 让两个线程“看起来并行、实际只能一个一个跑”；多进程各自独立 GIL，真正同时跑。→ [GIL](../python/GIL.md)

**预期**：单线程 ≈ 多线程（甚至更慢），多进程 ≈ 一半时间。
**为什么**：GIL 让多线程串行执行字节码，CPU 密集白搭；多进程各自独立 GIL 才真并行。→ [GIL](../python/GIL.md)

### 实验 2：asyncio 并发 + CPU 阻塞现象（⭐⭐⭐ 必做）

**知识点**：协程怎么并发；CPU 密集如何阻塞事件循环

```python
# asyncio_demo.py
import asyncio, time

async def io_task(i):
    await asyncio.sleep(1)      # 模拟 IO（不阻塞，交还控制权）
    return i

async def cpu_block():
    s = sum(i*i for i in range(30_000_000))   # CPU 密集（阻塞！）
    print("cpu 结果:", s)

async def heartbeat():
    for _ in range(10):
        print(f"  ❤ heartbeat {time.strftime('%X')}")
        await asyncio.sleep(0.3)

async def main():
    # ① 并发：3 个 1 秒任务应只花 ~1 秒
    t = time.time()
    await asyncio.gather(io_task(1), io_task(2), io_task(3))
    print(f"并发3任务耗时: {time.time()-t:.2f}s   ← ~1秒，不是3秒")

    # ② CPU 阻塞：heartbeat 会卡住
    asyncio.create_task(heartbeat())
    await asyncio.sleep(1)       # heartbeat 正常跳
    print(">>> 开始 CPU 密集，heartbeat 将停止")
    await cpu_block()            # 期间 heartbeat 完全不跳！
    await asyncio.sleep(1)

asyncio.run(main())
```

**预期**：并发 3 任务 ~1 秒；CPU 密集期间 heartbeat 停止跳动。
**为什么**：`await` 交还控制权才能并发；CPU 计算独占主线程，事件循环卡死。→ [异步如何实现的](../计算机原理/异步如何实现的.md)

### 实验 3：深浅拷贝的坑（⭐⭐）

```python
# copy_trap.py
import copy
a = [[1, 2], [3, 4]]

b = copy.copy(a)          # 浅拷贝
b[0][0] = 99
print("浅拷贝后 a:", a)    # [[99,2],[3,4]] ← 内层被改了！

c = copy.deepcopy(a)      # 深拷贝
c[0][0] = 0
print("深拷贝后 a:", a)    # 不变，完全独立
```

**为什么**：浅拷贝只复制外层，内层 list 仍是共享引用；深拷贝递归复制所有层级。→ [深拷贝与浅拷贝](../python/深拷贝与浅拷贝.md)

### 实验 4：默认参数陷阱 + 闭包延迟绑定（⭐⭐⭐ 高频）

```python
# closure_trap.py
# ① 默认参数只创建一次
def add(item, lst=[]):
    lst.append(item); return lst
print(add(1), add(2))     # [1] [1,2]   ← 第二次带上了第一次的！

# ② 闭包延迟绑定
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])          # [2,2,2]  ← i 引用循环结束值
print([(lambda i=i: i)() for i in range(3)])  # [0,1,2]  ← 修正：默认参数捕获
```

**为什么**：① 默认参数在定义时求值一次，被共享；② 闭包捕获变量而非值，循环结束后 i=2。→ [深拷贝与浅拷贝](../python/深拷贝与浅拷贝.md)、[闭包](../python/闭包.md)

### 实验 5：`==` 与 `is` 的小整数缓存（⭐⭐）

```python
# is_vs_eq.py
a, b = 256, 256
print(f"256: a is b = {a is b}")   # True（CPython 缓存 -5~256）

a, b = 257, 257
print(f"257: a is b = {a is b}")   # False（超出缓存，不同对象）
print(f"257: a == b = {a == b}")   # True（值相等）
```

**为什么**：CPython 缓存小整数，256 复用同一对象；257 各建新对象。→ 比较值永远用 `==`。→ [==与is的区别](../python/==与is的区别.md)

### 实验 6：手写装饰器（计时）（⭐⭐）

```python
# decorator.py
import time, functools

def timer(func):
    @functools.wraps(func)          # 保留原函数元信息
    def wrapper(*args, **kwargs):
        t = time.time()
        result = func(*args, **kwargs)
        print(f"[{func.__name__}] 耗时 {time.time()-t:.3f}s")
        return result
    return wrapper

@timer          # 等价于 slow = timer(slow)
def slow():
    time.sleep(0.5); return "done"

print(slow())            # 自动打印耗时
print(slow.__name__)     # 'slow'（因为 @wraps），不是 'wrapper'
```

**为什么**：装饰器 = 高阶函数 + 闭包，`@deco` 是 `f=deco(f)` 的语法糖。→ [装饰器](../python/装饰器.md)

### 实验 7：生成器省内存（⭐）

```python
# generator.py
import sys
N = 1_000_000
big_list = [i*i for i in range(N)]      # 一次性生成
big_gen  = (i*i for i in range(N))      # 惰性，按需生成
print(f"list 内存: {sys.getsizeof(big_list)} 字节")   # ~8MB
print(f"gen  内存: {sys.getsizeof(big_gen)} 字节")    # ~200 字节（固定！）
print("gen 取前5:", list(x for _, x in zip(range(5), big_gen)))
```

**为什么**：生成器用 yield 暂停恢复，不一次性占用内存，适合大数据流。→ [生成器](../python/生成器.md)

### 实验 9：CPU 密集让整个服务假死（⭐⭐⭐ 必做）

```javascript
// block-demo.js   先运行，再开两个终端测
const http = require("http")
function fib(n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2)
}

http
  .createServer((req, res) => {
    if (req.url === "/heavy") {
      res.end("fib=" + fib(42))
    } // CPU 密集，卡几秒
    else {
      res.end("ok")
    }
  })
  .listen(3000, () => console.log("http://localhost:3000"))

// 测试：一个终端 curl http://localhost:3000/heavy（卡住计算）
// 同时另一终端 curl http://localhost:3000（也会卡住！虽然它很快）
// → 整个 Node 被一个 CPU 任务卡死
```

**为什么**：单线程 + 非抢占式，CPU 计算独占主线程，所有请求被堵。→ [Node基础与架构](../nodejs/Node基础与架构.md)、[异步如何实现的](../计算机原理/异步如何实现的.md)

### 实验 10：`forEach` + `async` 的坑（⭐⭐⭐ 高频）

```javascript
// foreach-async.js
const arr = [1, 2, 3]
const save = async (x) => {
  await new Promise((r) => setTimeout(r, 100))
  console.log("saved", x)
}

// ❌ forEach 不等 async
console.log("--- forEach ---")
arr.forEach(async (x) => {
  await save(x)
})
console.log("done") // 立即打印 done，save 还没执行！

// ✅ 正确：for...of 串行 / Promise.all 并发
setTimeout(async () => {
  console.log("--- for...of ---")
  for (const x of arr) await save(x) // 串行，saved 1 2 3 然后...
  console.log("done2")
}, 200)
```

**为什么**：`forEach` 不等待 async 回调；要等用 `for...of` 或 `Promise.all(arr.map(...))`。→ [Node异步编程](../nodejs/Node异步编程.md)

### 实验 11：Stream 省内存（⭐⭐）

```javascript
// stream-vs-readfile.js
const fs = require("fs")
// 造一个 500MB 大文件（先运行一次）
// fs.writeFileSync('big.bin', Buffer.alloc(500*1024*1024));

// ❌ readFile 一次性载入，大文件爆内存
// fs.readFile('big.bin', (err, data) => console.log('读了', data.length));

// ✅ Stream 边读边处理，内存恒定
const { pipeline } = require("stream/promises")
;(async () => {
  let size = 0
  await pipeline(fs.createReadStream("big.bin"), async function* (source) {
    for await (const chunk of source) size += chunk.length
  })
  console.log("Stream 处理完:", size, "字节，内存平稳")
})()
```

**为什么**：Stream 分块处理，不一次性载入，处理 GB 级文件不爆内存。→ [Node模块系统与Stream](../nodejs/Node模块系统与Stream.md)

### 实验 12：手写简易事件循环（⭐⭐⭐）

```javascript
// diy-event-loop.js   理解事件循环本质：任务队列 + 微任务
const macrotasks = [] // 宏任务队列
const microtasks = [] // 微任务队列

function mySetTimeout(cb) {
  macrotasks.push(cb)
} // 模拟 setTimeout
function myThen(cb) {
  microtasks.push(cb)
} // 模拟 Promise.then

function runLoop() {
  // 取一个宏任务执行
  const task = macrotasks.shift()
  if (task) task()
  // 执行完清空所有微任务（关键！）
  while (microtasks.length) microtasks.shift()()
  // 还有宏任务就继续
  if (macrotasks.length) runLoop()
}

console.log("1")
mySetTimeout(() => console.log("2 宏任务"))
myThen(() => console.log("3 微任务"))
console.log("4")
runLoop()
// 输出：1 4 3 2  ← 微任务在宏任务前
```

**为什么**：亲手实现「宏任务 → 清空微任务 → 下一个宏任务」的循环，就懂了事件循环的核心。→ [Node事件循环](../nodejs/Node事件循环.md)

### 实验 13：手写 async/await 原理（generator）（⭐⭐⭐）

```python
# diy_asyncawait.py   async/await 底层是 generator
# 用 generator 模拟 async/await 的"暂停-恢复"

def fake_async():
    """一个'协程'：用 yield 暂停"""
    print("step1: 开始")
    x = yield "等IO"        # 暂停，等事件循环恢复并传回结果
    print(f"step2: 收到 {x}, 继续")
    y = yield "再等一次"
    print(f"step3: 收到 {y}, 完成")

def event_loop(gen):
    """事件循环：驱动协程，模拟 IO 完成后传回数据"""
    result = None
    try:
        while True:
            what = gen.send(result)    # 恢复协程，拿到它要等什么
            print(f"  [loop] 协程要求: {what}，模拟IO完成后传回数据")
            result = "IO结果"           # 模拟异步 IO 的返回值
    except StopIteration:
        print("协程结束")

event_loop(fake_async())
```

**输出**：

```
step1: 开始
  [loop] 协程要求: 等IO，模拟IO完成后传回数据
step2: 收到 IO结果, 继续
  [loop] 协程要求: 再等一次，模拟IO完成后传回数据
step3: 收到 IO结果, 完成
协程结束
```

**为什么**：async/await 的底层就是 generator——`yield` 暂停、`send` 恢复、事件循环驱动。亲手写一遍就懂协程不是魔法。→ [异步如何实现的](../计算机原理/异步如何实现的.md)、[生成器](../python/生成器.md)
