## 别名
- The Escape Hatch
- Escape Hatch Architecture
- Design for Replacement

## Description

可逃逸架构的核心思想是"为随时被替换而设计"。它通过将业务核心逻辑从技术框架中抽离为纯函数，并采用标准协议（如 MCP、OpenAPI）而非绑定特定框架来连接各层组件，从而在技术快速迭代的环境中获得架构韧性。在代码结构层面，这一原则体现为 Tools 定义集中在通用 modules 模块中，Agent 仅引用工具的 Schema 定义而不直接包含工具实现逻辑，通过继承和使用机制灵活挂载和调用工具，使工具的修改与扩展不会影响已有 Agent。

该架构采用三层结构：能力层提供具体服务，协议层（逃生舱）基于标准协议实现组件间解耦通信，运行时层保持无状态并按需加载工具。以"底层组件切换时 24 小时内完成迁移、核心逻辑零修改"为可量化的架构验收标准，确保系统在模型替换（如 GPT-4 换 DeepSeek）或框架切换（如 LangGraph 换 PydanticAI）时，业务逻辑获得"永生"。

## 架构层级
可逃逸架构采用三层结构设计：
- **能力层**：提供具体服务，包括各类工具、数据源和外部系统集成
- **协议层（逃生舱）**：采用 [[concepts/协议优于框架|协议优于框架]] 原则，基于 MCP / OpenAPI 标准实现组件间标准化通信，作为「逃生舱」确保能力层与运行时层的解耦
- **运行时层**：Agent 运行时保持无状态（Stateless Context），负责意图识别和任务执行，在运行时按需加载所需工具（Load Tools at Runtime），避免上下文窗口压力

## 关键特征
- **核心逻辑剥离（纯函数）**：将业务核心逻辑从技术框架中抽离，以纯函数形式存在，不依赖任何具体的技术实现
- **协议优于框架（MCP标准）**：采用标准协议（如MCP、OpenAPI）而非绑定特定框架，协议层作为「逃生舱」确保组件间通信契约稳定且可替换
- **模型无关性（网关层调用）**：通过统一的网关层调用LLM，隔离业务逻辑与具体模型实现，实现模型的透明切换
- **路由架构与按需加载（渐进式披露）**：采用路由架构进行模块编排与按需加载，运行时层保持无状态，仅按需加载所需工具，避免上下文污染
- **工具定义与引用分离**：Tools 定义集中在通用 modules 模块中，Agent 仅引用工具的 Schema 定义而非直接包含实现逻辑，通过继承和使用机制灵活挂载工具，实现工具修改扩展对已有 Agent 的零影响
- **24小时迁移承诺**：以"底层组件切换时24小时内完成迁移、核心逻辑零修改"为可量化的架构验收标准

## 应用
- **企业级Agent系统**：在客服Agent、舆情分析Agent等企业应用中，保障底层模型或编排框架的平滑迁移
- **AI架构治理**：作为集团或团队内部的架构标准，指导新项目的架构设计和技术选型
- **技术债防控**：在技术快速迭代的环境中（如LLM、Agent框架频繁更新），防止技术绑定带来的系统性风险
