# 普通业务项目分支管理规范 - Summary

## 来源
- 原始文件：[[../../架构/应用开发规范/分支管理]]
- 录入时间：2026-07-28

## 核心内容
本文档定义了一套适用于普通业务项目的 Git 分支管理规范。文档确立了五种核心分支类型：master 主分支保持绝对干净，仅用于正式版本发布；[[concepts/开发分支|开发分支]]与[[concepts/修复分支|修复分支]]均从 master 拉取，并严格遵循[[concepts/按版本号分层|按版本号分层]]的命名格式。在流转机制上，所有提测代码汇总至 [[entities/test|test]] 分支进行测试环境部署；验收通过后合并至 [[entities/release|release]] 分支统一打 Tag 发布，最终回流 master。

此外，文档系统性地阐述了多分支并行开发时的[[concepts/冲突处理|冲突处理]]流程，强调必须通过手动[[concepts/rebase|rebase]]到 master 以形成代码同步闭环。文档还指出了当前工程实践中的环境治理痛点，建议落实[[concepts/测试规范|测试规范]]，明确区分[[concepts/开发环境|开发环境]]与[[concepts/预发布环境|预发布环境]]，以保障测试环境的稳定性与纯净性。

## 关键实体
- [[entities/git|Git]]：实现所有分支管理规范的底层版本控制系统
- [[entities/test|test]]：测试环境发布分支，承担开发代码的汇总与部署功能
- [[entities/release|release]]：正式发布分支，负责版本 Tag 打点与生产环境发布

## 关键概念
- [[concepts/master分支保护策略|master分支保护策略]]：确保主分支始终代表生产环境稳定状态的核心基石
- [[concepts/灰度与回滚|灰度与回滚]]：通过 release 分支打 Tag 机制实现版本回溯与快速回滚
- [[concepts/冲突处理|冲突处理]]：解决多分支并行开发场景下代码同步的方法论
- [[concepts/测试规范|测试规范]]：倡导 dev 与 test 环境分离的环境隔离标准

## 要点
- **主分支保护**：master 分支保持干净，仅接受来自 release 的合并，所有迭代与修复必须从 master 拉取新分支
- **命名标准化**：采用版本号+日期的命名格式（如 `v4.x.x-2025xxxx` 和 `fix4.x.x-2025xxxx`），分支用途一目了然
- **版本可追溯**：release 分支统一打 Tag 发布，支持快速回滚至历史稳定版本，保障线上稳定性
- **闭环同步机制**：多分支并行时按版本号顺序依次提测，上线分支代码必须手动 rebase 到 master 形成发布闭环
- **环境治理优化**：建议构建 `dev → test → 预发布 → 生产` 的完整环境链路，避免测试数据污染
