# 面向极速迭代的防御性架构标准——可逃逸架构 - Summary

## 来源
- 原始文件: [[../../架构/应用开发规范/“可逃逸架构”设计模式]]
- 收录时间: 2026-07-28

## 核心内容
本文针对AI技术栈[[concepts/半衰期|半衰期]]仅3个月的现状，提出了一套防御性架构设计标准——[[concepts/可逃逸架构|可逃逸架构]]，核心理念为"Design for Replacement（为随时被替换而设计）"。文章以[[entities/deepseek|DeepSeek]] V3发布后企业面临的模型切换困境为切入点，指出紧耦合是AI项目最大的技术债。

架构建立在四大逃逸设计原则之上：[[concepts/核心逻辑剥离|核心逻辑剥离]]（纯函数化业务逻辑）、[[concepts/协议优于框架|协议优于框架]]（采用MCP标准）、[[concepts/模型无关性|模型无关性]]（通过[[entities/litellm|LiteLLM]]/[[entities/oneapi|OneAPI]]等网关层调用）以及[[concepts/路由架构与按需加载|路由架构与按需加载]]（[[concepts/渐进式披露|渐进式披露]]的L1 Router → L2 Worker分层模式）。后端要求实现[[concepts/client-server物理隔离|Client-Server物理隔离]]和[[concepts/pydantic-first|Pydantic First]]状态管理；前端推行[[concepts/生成式界面|生成式界面]]与[[concepts/流式优先|流式优先]]规范。对于存量系统，倡导[[concepts/code-first-rpa|Code-First RPA]]策略并严格执行[[concepts/读写分离|读写分离]]。最终通过[[concepts/消防演习|消防演习]]压力测试验证架构的可逃逸能力。

## 要点
- **AI技术栈半衰期仅3个月**，紧耦合是AI项目最大的技术债，所有依赖项（LLM模型、Agent框架、RPA工具等）都必须被视为[[concepts/临时组件|临时组件]]。
- **考核红线**：底层模型或编排框架切换时，必须在**24小时内**完成迁移，且业务核心逻辑代码**零修改**。
- **四大逃逸设计原则**：[[concepts/核心逻辑剥离|核心逻辑剥离]]（删掉框架import仍能跑通单测）、[[concepts/协议优于框架|协议优于框架]]（工具封装为MCP/OpenAPI）、[[concepts/模型无关性|模型无关性]]（改配置而非改代码）、[[concepts/路由架构与按需加载|路由架构与按需加载]]（通过[[concepts/8k挑战|8k挑战]]）。
- **后端规范**：Agent与工具实现[[concepts/client-server物理隔离|物理隔离]]，状态管理遵循[[concepts/pydantic-first|Pydantic First]]，严禁传递无结构Dict或用正则解析AI输出。
- **前端规范**：[[concepts/生成式界面|生成式界面]]要求新增场景前端代码零变更；[[concepts/流式优先|流式优先]]要求首字响应时间（TTFT）< 1秒。
- **存量系统处理**：推行[[concepts/code-first-rpa|Code-First RPA]]，严禁[[entities/影刀|影刀]]等低代码RPA工具，严格执行[[concepts/读写分离|读写分离]]（写操作封装为含Pre-check的固定工作流）。
- **消防演习验证**：测试A（模型大挪移）要求5分钟内通过改配置完成模型切换；测试B（框架大逃杀）要求半天内完成框架迁移，拒绝成为[[concepts/框架奴隶|框架奴隶]]。
